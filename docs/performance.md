# Performance

This page explains how `tracelens` currently validates local scale and command performance.

The project target for the first version is local OpenTelemetry trace analysis. Performance validation focuses on parsing, graph construction, and core CLI commands over synthetic OTLP JSON/JSONL files.

## Current Scale Target

The milestone target is:

```text
5k to 50k spans should parse, build graphs, and run core analysis commands within practical local CLI latency.
```

The current benchmark runner supports 5k and 50k span cases by default.

## Local Benchmark Runner

Run:

```bash
python3 tools/run_perf_benchmark.py
```

Default coverage:

```text
spans: 5000,50000
formats: json
shapes: balanced
commands: validate,summary,list-traces,services,critical-path,detect
iterations: 3
```

The runner also supports `timeline` for targeted checks:

```bash
python3 tools/run_perf_benchmark.py \
  --spans 50000 \
  --traces 20 \
  --formats json \
  --shapes balanced \
  --commands timeline \
  --iterations 1
```

`timeline` is not part of the default CI smoke command list yet because it renders one row per span in the selected trace. Use a focused run when changing timeline layout or rendering behavior.

For a focused 50k `detect` run:

```bash
python3 tools/run_perf_benchmark.py \
  --spans 50000 \
  --traces 20 \
  --formats json \
  --shapes balanced \
  --commands detect \
  --iterations 3
```

The runner writes:

```text
perf-data/
perf-results/
```

Both directories are ignored by Git.

## Local Acceptance Pipeline

Before committing local changes, run the acceptance pipeline:

```bash
tools/run_local_acceptance.sh
```

It runs the standard Rust checks, installs `tracelens` into `.local/tracelens`, then executes the installed binary against representative fixtures.

To trigger it automatically before each local commit, run once:

```bash
tools/setup_local_hooks.sh
```

Git does not enable repository hooks automatically after clone, so each developer needs this one-time setup. See [Local acceptance pipeline](local-acceptance-pipeline.md).

## Synthetic Fixtures

Fixtures are generated by:

```bash
python3 tools/generate_synthetic_traces.py
```

The generator can produce:

- OTLP JSON
- OTLP JSONL
- balanced traces
- deep traces
- wide traces
- overlapping traces
- attribute-heavy traces

Example:

```bash
python3 tools/generate_synthetic_traces.py \
  --output perf-data/json-balanced-50000s-20t.json \
  --format json \
  --shape balanced \
  --spans 50000 \
  --traces 20
```

## GitHub Actions Benchmark

The benchmark workflow can run manually or on main updates.

Default benchmark inputs now include:

```text
spans: 5000,50000
commands: validate,summary,list-traces,services,critical-path,detect
```

Benchmark reports are added to the GitHub Actions summary and uploaded as artifacts.

## Interpretation

Benchmark numbers are smoke-test signals, not a formal hardware-independent SLA.

Use them to answer:

- Did a command regress obviously?
- Does `detect` still handle 50k spans?
- Does a timeline layout change need a focused `timeline` benchmark?
- Are generated fixtures and benchmark outputs staying out of Git?
- Does a new analysis command need targeted optimization before it becomes part of the default workflow?
